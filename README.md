# CheckStock

Небольшой веб-прототип для менеджера: **где сейчас товар**, сколько доступно на ФФ и что уже уехало (перемещение / FBO / FBS).

Стек по заданию: **Python · FastAPI · PostgreSQL**. UI — одна простая страница без фреймворка. Всё поднимается через Docker Compose.

---

## Быстрый старт

Нужны **Docker Desktop** (или другой Docker Engine) и Docker Compose.

На Windows: [Docker Desktop](https://www.docker.com/products/docker-desktop/) → после установки убедитесь, что в терминале есть `docker compose version`.

```bash
docker compose up --build
```

Открыть: [http://localhost:8001](http://localhost:8001)

API-документация: [http://localhost:8001/docs](http://localhost:8001/docs)

Остановка:

```bash
docker compose down
```

Полный сброс БД (том Postgres):

```bash
docker compose down -v
docker compose up --build
```

При старте API создаёт таблицы и один раз заливает тестовые данные из брифа.

| Артикул | Товар      | Север | Юг |
|---------|------------|------:|---:|
| SKU-101 | Органайзер |    10 |  6 |
| SKU-102 | Контейнер  |     5 |  0 |
| SKU-103 | Корзина    |     0 |  4 |

## Что умеет прототип

1. **Экран остатков** — по каждому SKU и ФФ: физически на складе, доступно, в резерве FBS. Отдельно блоки «в пути»: между ФФ, на маркетплейс (FBO), к клиенту (FBS).
2. **Склады** — создать / переименовать / удалить ФФ. Удаление **мягкое**: остатки и история сохраняются, товар продолжает числиться на удалённом ФФ (колонка помечена «удалён»).
3. **Движения** — приход; отправка и приёмка перемещения между ФФ.
4. **FBS** — резерв (блокирует доступность), отмена резерва, отправка к клиенту.
5. **FBO** — отгрузка с ФФ → «в пути на МП» → приёмка на маркетплейсе.
6. **История** — append-only журнал операций: товар, количество, откуда/куда, комментарий.
7. **Идемпотентность** — повтор с тем же `idempotency_key` не списывает товар второй раз (`replayed: true`).
8. **Нехватка на выбранном ФФ** — если на выбранном складе мало, а суммарно по активным ФФ хватает, API отвечает `409` с альтернативами.

## Ключевые решения

### 1. Остаток = `on_hand` + `reserved_fbs`

На паре `(warehouse, product)` хранится:

- `on_hand` — физически на ФФ
- `reserved_fbs` — заблокировано под FBS
- **доступно** = `on_hand - reserved_fbs` (считается, не хранится отдельно)

Так проще держать инварианты: резерв не может «висеть» без физического остатка, а отправка FBS уменьшает и резерв, и `on_hand`.

### 2. «В пути» — отдельные сущности, не строки баланса

Пока товар едет, он уже списан с ФФ-источника и ещё не попал (или никогда не попадёт) на другой ФФ:

| Сценарий              | Что происходит с балансом                         | Где видно «в пути»        |
|-----------------------|---------------------------------------------------|---------------------------|
| Перемещение ФФ → ФФ   | −`on_hand` у источника; +`on_hand` при приёмке    | `transfer_shipments`      |
| FBO                   | −`on_hand` при отправке; приёмка только статус    | `fbo_shipments`           |
| FBS к клиенту         | −`reserved` и −`on_hand` при отправке             | `fbs_orders` (shipped)    |

Итог на экране остатков: физика по ФФ + три списка in-transit. Менеджер видит и «где лежит», и «что уже уехало».

### 3. Журнал операций + idempotency key

Каждое подтверждающее действие пишет строку в `operations` с **уникальным** `idempotency_key`.

- Первый запрос меняет остатки и создаёт операцию.
- Повтор с тем же ключом возвращает прежний результат и **не** трогает остатки.

Это закрывает требование «повторное подтверждение не списывает товар дважды» (двойной клик, ретрай сети, повтор в UI).

### 4. Удаление ФФ — soft delete

Жёсткое удаление ломает историю и «где числится товар». Поэтому:

- `warehouses.is_deleted = true`
- строки `stock_balances` остаются
- удалённый ФФ виден в таблице остатков с пометкой
- новые операции на него запрещены

Так выполняется: «при удалении сохраните остатки и историю».

### 5. Нехватка на выбранном ФФ

Если на выбранном складе `available < qty`, но суммарно по **активным** ФФ товара хватает, возвращается:

```json
{
  "code": "insufficient_on_selected_warehouse",
  "message": "...",
  "requested": 5,
  "available_on_selected": 0,
  "total_available": 5,
  "alternatives": [{"warehouse_name": "Север", "available": 5}]
}
```

Автоматически чужой ФФ не трогаем — менеджер явно выбирает источник. В UI это показывается предупреждением.

### 6. Простой UI на статике

Один HTML + CSS + JS, раздаётся FastAPI. Без React/Vite: меньше движущихся частей, проще запуск и проверка за один день. Для тестового прототипа этого достаточно.

## Проверка сценариев (ручной чеклист)

После `docker compose up --build` откройте UI или используйте `/docs`.

### A. Учёт после прихода / резерва / перемещения / отправки / приёмки

1. На «Остатках» сверьте seed: SKU-101 = 10/6, SKU-102 = 5/0, SKU-103 = 0/4.
2. **Приход**: +2 SKU-102 на «Юг» → Юг 2, доступно 2.
3. **Резерв FBS**: SKU-101, Север, 3 → физ 10, дост 7, резерв 3.
4. **Перемещение**: SKU-101, Север → Юг, 2 → Север физ 8; появляется «в пути между ФФ».
5. **Приёмка перемещения** → Юг физ +2, список «в пути» пустеет.
6. **Отправка FBS** по резерву → резерв снимается, физ −3, позиция в «к клиенту».
7. **FBO**: отправить 1 шт. с Юга → −1 с ФФ, строка «в пути на МП»; приёмка меняет только статус (на ФФ уже списано).
8. Вкладка **История** — все шаги на месте, остатки сходятся с действиями.

### B. Нехватка на выбранном ФФ

1. Возьмите SKU-102: на «Юге» 0 (или мало), на «Севере» есть остаток.
2. Попробуйте резерв/FBO/перемещение **с Юга** на количество, которого там нет.
3. Ожидание: предупреждение + `alternatives` с «Север», остатки не меняются.
4. Повторите операцию с «Севера» — проходит.

### C. Удаление ФФ с остатком

1. Удалите «Юг», пока на нём есть товар.
2. Склад помечается удалённым, **цифры остатков не пропадают**.
3. История сохраняется; создать приход на «Юг» нельзя.
4. На экране остатков видно, что товар числится на удалённом ФФ.

### D. Повторное подтверждение

В UI у открытых перемещений / FBO / FBS есть кнопка «Повторить …» — она шлёт **один и тот же** `idempotency_key` дважды.

Ожидание: второе сообщение «Повтор: операция уже была учтена», количества на остатках не удваиваются.

Автопроверка API после запуска:

```bash
python scripts/smoke_api.py
```

То же через curl:

```bash
# подставьте реальные UUID из /api/stock или /docs
curl -s -X POST http://localhost:8001/api/movements/receipt \
  -H "Content-Type: application/json" \
  -d "{\"idempotency_key\":\"demo-receipt-1\",\"product_id\":\"...\",\"warehouse_id\":\"...\",\"quantity\":1}"

# второй раз с тем же ключом — replayed: true, остаток +1 только один раз
curl -s -X POST http://localhost:8001/api/movements/receipt \
  -H "Content-Type: application/json" \
  -d "{\"idempotency_key\":\"demo-receipt-1\",\"product_id\":\"...\",\"warehouse_id\":\"...\",\"quantity\":1}"
```

## Полезные API

| Метод | Путь | Назначение |
|-------|------|------------|
| GET | `/api/stock` | Сводка остатков + in-transit |
| GET/POST/PATCH/DELETE | `/api/warehouses` | Склады (DELETE + `idempotency_key`) |
| POST | `/api/movements/receipt` | Приход |
| POST | `/api/movements/transfer/ship` | Отправка перемещения |
| POST | `/api/movements/transfer/receive` | Приёмка перемещения |
| POST | `/api/fbs/reserve` `/cancel` `/ship` | FBS |
| POST | `/api/fbo/ship` `/receive` | FBO |
| GET | `/api/operations` | История |

Все POST-подтверждения принимают `idempotency_key` в теле (для DELETE склада — query-параметр).

## Локальный запуск без Docker (опционально)

1. Поднять Postgres (или только сервис `db` из compose).
2. В `backend`:

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate
pip install -r requirements.txt
set DATABASE_URL=postgresql+psycopg://checkstock:checkstock@localhost:5432/checkstock
uvicorn app.main:app --reload --app-dir .
```
